# 한 사람 기준 인수인계 데이터셋

`오건우` 한 사람을 기준으로 만든 100건짜리 작은 데이터셋. 인수인계 화면을 실제 데이터로
시험하려고 만들었다.

## 무엇이 들어 있나

| 무엇 | 몇 |
|---|---|
| 문서 | 100 (슬랙 · 깃허브) |
| 업무 | 10 |
| 모순 | 2 |
| 노후 | 2 |
| 공백 | 2 |

조직도는 **새로 안 만든다.** 1,000건 뽑을 때 쓴 `generated_data/employee_directory.yaml`
그대로다 — 사람·부서·깃허브 로그인이 달라지면 이미 올려 둔 조직과 안 이어진다.

## 돌리는 법

```bash
cd EnterpriseRAG-Bench
.venv/bin/python -m new_data.generate --out new_data/sources            # 100건
.venv/bin/python -m new_data.generate --out new_data/sources --limit 8  # 맛보기
```

`.env` 는 1,000건 때와 같은 것을 쓴다(`LLM_PROVIDER`, `DEEPSEEK_API_KEY` 등).

끝나면 `new_data/manifest.json` 에 무엇을 심었는지 남는다.

## 어떻게 만드나

**주제를 모델에게 안 맡긴다.** `scenario.py` 가 업무 열 개와 심을 것 여섯 개를 정해 두고,
생성기는 그 칸을 채우기만 한다. 1,000건 때는 모델이 주제까지 정했는데, 그러면 모순·노후·
공백이 **몇 건 나올지 알 수 없다.**

**심은 문장은 글자 그대로 들어가야 한다.** 모델이 말을 바꾸면 린트가 못 잡는다 —
모순은 주어·속성이 같아야 짝이 되고, 노후는 갱신 주기가 적혀 있어야 오래됐는지 잴 수 있다.
그래서 쓴 뒤에 문장이 그대로 있는지 보고, 없으면 그 자리에서 다시 시킨다(최대 세 번).

**그런데 문장만 같아서는 모자랐다.** 첫 판에서 모순이 한 건도 안 잡혔다. 두 문서에 문장을
글자 그대로 넣었는데 추출기가 주어와 속성을 다르게 잘랐기 때문이다.

```
80억    subject=바로배송 인프라 증설             predicate=약정 계약 규모
100억   subject=바로배송 인프라 증설 약정 계약 규모  predicate=규모
```

주어가 다르니 짝이 아니고, 그래서 모순이 아니다. 같은 문장이라도 **앞뒤 맥락이 다르면
다르게 잘린다.**

그래서 심은 문장이 든 글 맨 뒤에 자를 자리를 정해 주는 한 줄을 더 박았다.

```
바로배송 인프라 증설 · 약정 계약 규모 = 100억 원
```

Baton 이 클레임을 이 모양으로 그리므로 추출기가 같은 자리에서 자를 확률이 높다. 슬랙에서
흔히 보는 요약 한 줄로도 읽혀 글이 어색해지지 않는다. 무엇을 박았는지는
`manifest.json` 의 `triples` 에 남는다.

**지어낸 숫자도 걷어냈다.** 모델이 「위키엔 73억으로 되어 있던 것 같은데」 같은 말을
덧붙이면, 같은 주어·속성으로 클레임이 하나 더 생겨 어느 것이 심은 모순인지 흐려진다.

**한정 표현도 걷었다.** 「영업 쪽 기준으로 보면 100억」, 「메일 본문 기준으로는 80억」 처럼
어느 기준인지 밝히면 그것이 적용 범위(`scope`)로 뽑힌다. 린트는 범위가 다르면 **별개의
주장**으로 보고 짝을 깬다. 같은 것을 두고 다투는 글이어야 모순이 된다.

## 고치는 법

이미 만든 100건을 다시 뽑지 않고 고칠 수 있다. 삼단 줄을 박는 것도, 잡음을 걷는 것도
여기서 한다.

```bash
.venv/bin/python -m new_data.fix_planted --root new_data/sources --dry-run
.venv/bin/python -m new_data.fix_planted --root new_data/sources
.venv/bin/python -m new_data.check --root new_data/sources        # 규격 · 심은 문장 · 못 쓸 글자
```

`fix_planted` 는 두 번 돌려도 같은 결과다. `check` 는 어긋난 것이 있으면 종료 코드 1 을 준다.

### 노후가 심은 두 건만 남게

노후 검사는 **시간에 따라 바뀌는 속성**만 본다. 그 판정은 속성 사전이 하는데, 기준은
「그 속성의 클레임에 적용 시점이 붙은 적이 있는가」다(`PredicateDictionaryMatcher`).
그래서 심은 사실에 「2025년 3분기부터 적용」 을 같이 적어 뒀다 — 안 적으면 그 속성이
노후 검사 대상에서 아예 빠진다.

문서 하나가 클레임을 여럿 낳는 것도 줄였다. 되받는 말에서 사실을 다시 진술하면 같은
클레임이 두세 번 잡히고, 「다음 분기 넘어가기 전에」 같은 미래 시점은 곁가지 클레임이 된다.

린트의 노후 문턱은 근거 시점 기준 180일이다. 100건을 열 달에 걸쳐 뿌려 놨더니 절반이
문턱 밖으로 나가 노후가 176건 잡혔고, 심은 두 건이 그 안에 파묻혔다.

```bash
.venv/bin/python -m new_data.shift_dates --root new_data/sources --dry-run
.venv/bin/python -m new_data.shift_dates --root new_data/sources
```

문턱 밖 문서 중 `stale-*` 둘만 그 자리에 두고 나머지를 문턱 안으로 옮긴다. **시간 순서는
지킨 채 구간만 압축한다** — 옛 문서가 갑자기 제일 최근이 되면 업무의 흐름이 뒤집힌다.

문서 하나는 통째로 같은 폭만큼 민다. 스레드 시각만 옮기고 본문에 적힌 날짜를 두면
「2026-01-05 에 정했다」는 글이 4월에 쓰인 것이 된다. ISO 날짜와 함께 「2025년 10월」,
「11월 24일」, 「10/6~10/12」 까지 민다. 「이번 주」 같은 상대 표현은 안 건드린다 —
밀어도 뜻이 안 변한다.

**단독 슬래시 숫자는 손대지 않는다.** 이 데이터의 슬래시는 거의 다 CIDR 대역
(`10.30.0.0/16`)이고 `SEV-1/2` 나 최소/최대 `2/6` 도 있다. 하나라도 밀면 네트워크 구성이
조용히 망가진다. 그래서 범위로 적힌 것(`10/6~10/12`)만 날짜로 본다.

**문서 시각은 최근인데 본문이 옛날을 가리키는 경우도 당긴다.** 「버킷에 2025년 2월 것부터
있네요」 같은 회고 문장인데, 추출기가 그 시점을 근거로 뽑아 노후로 잡는다. 문서를 통째로
밀 수는 없으니 본문의 그 표기만 문턱 안으로 당기고, 문서 시각보다는 앞이게 둔다 —
회고가 미래를 가리키면 글이 말이 안 된다.

문서 모양은 커넥터가 파싱하는 그 규격이다. `src/utils/connector_schema.py` 로 검사하므로
1,000건과 같은 경로로 수집된다.

## 심은 것

### 모순 2

**바로배송 인프라 — 약정 계약 규모.** 한 문서는 100억, 다른 문서는 80억이라 적는다.
계약을 맺은 사람이 퇴사해서 **사람에게 물어 풀 수 없는** 모순이다. 산정 근거가 어디에도 없다.

**모니터링 대시보드 — 담당자.** 한 문서는 오건우와 정하늘 둘, 다른 문서는 정하늘 혼자라고
적는다. 어느 쪽이 맞는지 안 적혀 있다.

### 노후 2

노후의 기준은 **「시간이 지나면 값이 바뀌는 속성인데 근거가 그 주기보다 오래된 것」**이다.
그래서 주기를 문서 안에 같이 적어 뒀다 — 안 적으면 오래된 것인지 잴 근거가 없다.

**온콜 1차 대응자.** 분기마다 교대하기로 해 놓고 2025-07 이후 갱신 기록이 없다.

**주문 DB 인스턴스 등급.** 분기마다 사용량을 보고 조정한다고 해 놓고 2025-09 이후 없다.

### 공백 2

공백은 **「여러 번 가리키는데 정의가 어디에도 없는 것」**이다. 한 번만 나오면 그냥 안 쓴
것이고, 여러 곳에서 당연한 듯 참조해야 「왜 이게 없지」가 된다.

**운영 배포 승인자.** 여러 문서가 「승인을 받은 뒤에만 진행한다」고 적는데 **누가 승인자인지**
아무 데도 없다.

**P1 장애 기준.** 「P1 은 즉시 호출」, 「이번 건은 P1 로 분류」라고 쓰는데 **무엇이 P1 인지**
정의한 문서가 없다.

## 업무 열 개

온콜 대응 체계 · 배포 파이프라인 · RDS 운영 · ECS 클러스터 · 모니터링 대시보드 ·
비용 최적화 · 보안 점검 · 로그 수집 · 네트워크 구성 · 바로배송 인프라

Baton 은 지식 페이지의 `부서/프로젝트` 경로로 업무를 만든다. 그래서 프로젝트 이름이 문서에
또렷하게 나와야 업무로 잡힌다 — 열 개가 서로 헷갈리지 않게 이름을 벌려 뒀다.

문서가 이미 커넥터 규격이라 그대로 올리면 된다. 조직도는 `tools/load_org_to_baton.py` 로

## 확인할 것

수집이 끝나면 이렇게 확인한다.

```
확인 요청함   모순 2 · 노후 2 · 공백 2 가 오건우 업무에서 나오는가
업무 이력     오건우에게 업무가 10개 잡히는가
인수인계      오건우로 시작하면 넘길 업무가 10개로 잡히는가
```

**개수가 정확히 맞지는 않을 수 있다.** 심은 것 말고도 모델이 쓴 평범한 기록에서 모순이
더 나올 수 있다 — 심은 여섯 개가 **반드시 들어 있다**는 것이 이 데이터셋의 약속이고,
그보다 더 나오는 것은 막지 않았다.
